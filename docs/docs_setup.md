At the **root of the repository, in a `docs/` folder**, next to `src/`, not inside it. `src/` is for code that gets built into the app; documentation is not part of the build. `docs/` at the root is the common convention, and GitHub renders markdown files there directly in the browser.

Documentation in this project splits into three places, depending on who reads it and when:

```
wannawatch/
  README.md                  ← entry point: what, how to run, links
  docs/
    adr/                     ← architecture decisions
      template.md
      0001-styling-approach.md
    experiments/             ← A/B test write-ups (stage 6)
    architecture.md          ← later: overview of how parts connect
  .github/
    pull_request_template.md
  src/
    components/
      MovieCard/
        MovieCard.stories.tsx  ← component docs live here (Storybook autodocs)
        MovieCard.mdx          ← only if a component needs longer usage notes
```

- **`README.md`**: the first thing a reviewer sees. Short: what the project is, setup commands, how to run tests and Storybook, links to the published Storybook and to `docs/`.
- **`docs/`**: project-level decisions and explanations that do not belong to a single component.
- **Next to the component**: usage docs for each component, generated by Storybook from stories and props. Keeping them beside the code means they get updated in the same PR as the component.

Optional: you can make the ADRs visible inside Storybook too, by adding `../docs/**/*.mdx` to the `stories` array in `.storybook/main.ts` and writing them as `.mdx`. I would keep them as plain `.md` on GitHub for now; it is simpler, and reviewers usually read ADRs in the repo.
